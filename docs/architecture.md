# معماری افزونه

## مرز مسئولیت‌ها

افزونه قیمت خود محصول را از WooCommerce CRUD تغییر می‌دهد. موجودی، رزرو موجودی، محاسبهٔ سبد، درگاه، وضعیت پرداخت، Refund و مبلغ ثبت‌شدهٔ سفارش در اختیار ووکامرس باقی می‌مانند. SQL اختصاصی فقط روی جدول‌های خود افزونه مجاز است؛ محصول و سفارش با کوئری مستقیم تغییر نمی‌کنند.

| لایه | مسئولیت |
| --- | --- |
| Bootstrap و composition root | بررسی وابستگی‌ها، Autoload و اتصال سرویس‌ها به Hookها |
| `Domain` | تبدیل دقیق مبلغ، برنامهٔ قیمت و مرزهای زمانی مستقل از وردپرس |
| `Infrastructure` | Migration، Repository کمپین، قفل محصول، ثبت رخداد و پاک‌سازی هدفمند کش |
| `Application` | انتخاب و اعتبارسنجی محصول، Snapshot، اعمال و بازیابی، چرخهٔ کمپین و صف |
| `Admin` و `Rest` | نمایش مدیریتی و درخواست‌های مجاز؛ بدون محاسبهٔ مالی در مرورگر |
| `Integration` | نمایش عمومی مشترک، Elementor، ارسال، انتساب سفارش و آمار |

## داده‌های پایدار

جدول‌های دارای پیشوند وردپرس شامل `exin_bf_campaigns` برای تنظیمات و نسخهٔ کمپین، `exin_bf_items` برای محصول، برنامه، Snapshot و نتیجهٔ عملیات، `exin_bf_locks` برای اطلاعات قفل و `exin_bf_audit` برای رخدادهای عملیاتی هستند. این جداسازی به‌دلیل نیاز به ایندکس، اجرای Batch، بازیابی و انحصار عملیات است. دادهٔ شخصی مشتری در این جدول‌ها یا Log افزونه ذخیره نمی‌شود.

Repository فیلدهای JSON را در مرز ذخیره‌سازی تبدیل می‌کند؛ مصرف‌کننده با آرایه کار می‌کند. Snapshot اولیه پس از افزودن محصول حفظ می‌شود و با هر کاهش قیمت بازنویسی نمی‌شود. Schema شمارهٔ `2` ستون `retry_state` را برای بودجه، موعد و نسخهٔ Retry نگه می‌دارد؛ ارتقای `1 → 2` با حفظ Snapshot تست شده است. ردیف Removed برای تاریخچه و افزودن مجدد امن حفظ می‌شود و از فهرست و شمارش محصولات مدیریتی کنار می‌رود. پیش از ارتقا، پشتیبان دیتابیس لازم است.

## چرخهٔ کمپین و محصول

کمپین از پیش‌نویس به زمان‌بندی‌شده و فعال می‌رود؛ توقف موقت اجرای تغییرات آینده را متوقف می‌کند. ادامه از قیمت صحیح زمان جاری شروع می‌شود. پایان طبیعی فرایند بازیابی را اجرا می‌کند. خطا و Conflict به‌صورت دادهٔ قابل بررسی باقی می‌مانند.

وضعیت محصول مستقل از وضعیت کمپین است. محصول فعال، ناموجود یا دارای Conflict می‌تواند در یک کمپین مشترک وجود داشته باشد. Variation با شناسهٔ قابل فروش خودش ذخیره می‌شود؛ Parent متغیر جایگزین Variation مالی نیست. محصولات Grouped، External و نوع ناشناخته پذیرفته نمی‌شوند.

## مالکیت قیمت و بازیابی

پیش از تغییر، وضعیت قیمت جاری با Snapshot یا آخرین وضعیت مورد انتظار مقایسه می‌شود. قصد عملیات پیش از نوشتن ثبت می‌شود تا قطع پردازش میان ذخیرهٔ محصول و ثبت نتیجه قابل تشخیص باشد. هر عملیات شناسه و نتیجهٔ پایدار دارد. عملیات تکراری نباید قیمت را دوباره کاهش دهد.

بازیابی تنها وقتی مجاز است که قیمت فعلی با وضعیت تحت کنترل افزونه هم‌خوانی داشته باشد. تغییر مدیر یا افزونهٔ خارجی باعث Conflict می‌شود؛ افزونه قیمت جدید را کورکورانه بازنویسی نمی‌کند. بازیابی مکرر پس از موفقیت اثر مالی تازه‌ای ندارد.

قفل اتمیک از `GET_LOCK` اتصال MySQL استفاده می‌کند؛ در دسترس‌نبودن آن عملیات مالی بسته می‌ماند و بدون قفل ادامه نمی‌دهد. ردیف‌های پایدار قفل اطلاعات تشخیصی را نگه می‌دارند. این قفل انحصار Jobهای افزونه و مسیرهای CRUD هماهنگ‌شده را فراهم می‌کند. نوشتن SQL مستقیم توسط کد خارجی، Object Cache نامعتبر و موتورهای قیمت در زمان نمایش می‌توانند از این مرز عبور کنند؛ مقایسهٔ وضعیت و تست Staging همچنان ضروری‌اند. هیچ تضمین عمومی برای شناسایی همهٔ افزونه‌های قیمت پویا وجود ندارد. Integrationهای قیمت پویا می‌توانند با فیلتر `exin_bf_dynamic_pricing_conflict` ناسازگاری خود را اعلام کنند؛ اختلاف قیمت View با قیمت Edit نیز بررسی می‌شود.

## زمان‌بندی و کش

تاریخ‌های ذخیره‌شده UTC هستند؛ مرز روز با منطقهٔ زمانی کمپین محاسبه می‌شود. Job نسخهٔ کمپین را بررسی می‌کند؛ درخواست قدیمی پس از توقف یا تغییر معتبر نادیده گرفته می‌شود. Job دیررس قیمت زمان فعلی را محاسبه می‌کند و قیمت‌های ازدست‌رفته را پشت سر هم اعمال نمی‌کند. اندازهٔ Batch برابر ۲۵ محصول است. بودجهٔ عملیات پیش از اجرای حساس ثبت می‌شود؛ سه Retry با فاصله‌های ۳۰، ۶۰ و ۱۲۰ ثانیه مجازند. Watchdog، Callback تکراری، قطع Worker و خطای ذخیرهٔ لاگ بودجه را از ابتدا شروع نمی‌کنند. پس از اتمام بودجه، محصول Conflict می‌شود و بررسی مجدد صریح مدیر لازم است.

تنظیم مدت نگهداری کمپین جاری روی مجموعهٔ Audit افزونه اعمال می‌شود. پاک‌سازی دوره‌ای Batch و سقف حجم دارد؛ حذف یک‌بارهٔ تمام تاریخچه یا Flush کش سایت انجام نمی‌شود.

پس از نوشتن محصول، کش و Transientهای همان محصول و Parent مرتبط بی‌اعتبار می‌شوند. پاک‌سازی کامل Redis یا Object Cache انجام نمی‌شود. کش کامل صفحه و CDN خارج از کنترل مستقیم افزونه‌اند؛ صفحات حساس باید از کش مستثنا یا با Integration واقعی Purge شوند.

## سفارش و گزارش

شناسهٔ کمپین هنگام ایجاد قلم سفارش، بر اساس عضویت معتبر و وضعیت همان لحظه ذخیره می‌شود. گزارش تاریخی بر این دادهٔ ثابت تکیه می‌کند؛ صرف حضور Product ID در کمپین فعلی یا تطابق تاریخ برای انتساب گذشته کافی نیست. اگر Job روزانه میان محاسبهٔ سبد و ایجاد سفارش اجرا شود، انتساب قلم منتخب حفظ می‌شود و مبلغ ذخیره‌شده را ووکامرس تعیین می‌کند؛ افزونه مبلغ سفارش را بازنویسی نمی‌کند. کنترل سخت‌گیرانهٔ مالکیت قیمت برای تغییر قیمت و ارسال رایگان همچنان مستقل برقرار است. شمارش سفارش یکتا، واحد فروش، درآمد اقلام و کل سفارش مرتبط جدا هستند. Refund و وضعیت مجاز گزارش بررسی می‌شوند. خواندن سفارش از CRUD ووکامرس انجام می‌شود تا با HPOS سازگار باشد.

گزارش حداکثر پنج صفحهٔ ۱۰۰ سفارش در هر درخواست پردازش می‌کند؛ Checkpoint خصوصی ادامهٔ درخواست بعدی را نگه می‌دارد. تا تکمیل، خروجی با `complete=false` و اطلاعات پیشرفت برمی‌گردد و نباید مجموع نهایی تلقی شود. تغییر سفارش/وضعیت/Refund کش و Checkpoint مربوط را بی‌اعتبار می‌کند. جمع ارزهای متفاوت انجام نمی‌شود و سفارش دارای ارز متفاوت از ارز جاری فروشگاه کنار گذاشته می‌شود.
